# Stability and performance audit, 2026-10-04

A read-only pass over the whole repo: the print server and Chrome extension,
the lobby signage app, the sync Worker and site, the Journey kiosk, both
Electron shells, CI, and the dependency tree. Every check in `ci.yml` was also
run locally. Nothing in this document has been changed in code yet.

**Baseline:** everything is green. 5,656 unit tests and 212 Playwright tests
pass with no flakes; lint, typecheck, both builds and the mirror check pass.
The findings below are latent: they bite on a club night, on switch day, or
after days of uptime, not in CI.

Each finding was verified against the source by a second reader. Line numbers
are against commit `c20327b`. Deliberate choices documented in the three
`CLAUDE.md` files were checked and are not listed as bugs (a short list of
those is at the end).

---

## The ten that matter most

Ranked by how likely each is to cost a club night or break switch day.

| # | Severity | Where | What |
| --- | --- | --- | --- |
| 1 | High | Chrome extension | Labels queued while the print server is down are silently discarded when it comes back |
| 2 | High | Print server | Every print and printer check blocks the whole Electron process, for up to about 100 s in the worst case |
| 3 | High | Lobby + Worker | The new live WebSocket has no liveness check: a half-open socket stays "connected" and deaf forever |
| 4 | High | Lobby | On switch day the service worker will cache the Worker's `/api` GETs forever |
| 5 | High | Print server | Duplicate-print guard is check-then-record across awaits, so overlapping requests both print |
| 6 | High | Lobby | Nothing resets "per night" state on a TV that stays up for days; tonight's count and milestones carry over |
| 7 | High | Printer app | Tray says "running" before the port is bound; a failed bind is logged to a console nobody sees |
| 8 | High | SWITCH.md | The runbook's bridge release versions (6.22.0, 1.1.0) are below or equal to what the feeds already serve, so following it would stop updates |
| 9 | High | Lobby | Self-update wedges for good if a second deploy lands while a screen is waiting to reload |
| 10 | High | Journey | Nothing supervises Chromium on the Pi: no restart, no watchdog, no nightly reboot |

### 1. Queued labels are dropped on flush (extension)

`printer/chrome-extension/content.js:3658-3671` (`onCheckin`), `:3736-3744`
(`doPrint` failure path), `:469-482` (`flushQueue`).

Every detection path calls `markPrinted()` before `doPrint()`. When the server
is unreachable, `doPrint` queues the payload, but the child is already in
`printedNames`. `flushQueue` then finds the same identity key in
`printedNames` and drops the item with "already printed this session".
Reconcile will not reprint either, because the child counts as printed. A
restart of the print app mid-rush (an auto-update, a crash, a driver hang past
35 s) loses every label queued in that window, with no warning.

Fix: keep a `queuedKeys` set; drop a flushed item only if its key is in
`printedNames` and not in `queuedKeys`. Add a test that lifts `queuePrint` and
`flushQueue`. Four more queue defects ride along: truncation drops the newest
(`saveQueue` does `q.length = 50`), `localStorage.setItem` is unguarded
(each item carries a base64 club logo), the item leaves storage before the POST,
and overlapping flushes have no in-flight flag and a 4xx poison item blocks the
head forever.

### 2. Synchronous PowerShell blocks the process (print server)

`printer/print-server/server.js:2572, 2584, 2612, 2682, 2691, 2952, 2981,
3571, 6048, 7111, 7203, 7254, 8424`. The server runs inside Electron's main
process (`printer/electron-app/main.js:601`).

Each print, printer probe, tune and PDF uses `execSync`, and the retry waits
use `Atomics.wait`. While one runs, no other request is served, timers stall,
and the tray and Settings window freeze. The code's own comments acknowledge
this. Worst case for one check-in with a hung driver, the tune on, and a
backup printer set is about 100 s with the event loop blocked. `/health`
blocks one to three seconds every minute spawning two PowerShells whether or
not anyone is at the door. The extension's 35 s timeout then retries, which
queues another blocking run.

Fix: promisified `execFile` behind one async print mutex (keeps today's
one-at-a-time ordering); `await setTimeout` instead of `Atomics.wait`; run the
`/health` probes on a background timer and serve the cached result. Longer
term, run the server in a `utilityProcess` the main process supervises.

### 3. No liveness check on the live channel (lobby)

`lobby/src/hooks/useSocket.js:376-406`.

The client sends `ping` every 25 s and discards `pong` without recording it.
There is no connect timeout either. After a Wi-Fi roam, router reboot or NAT
drop the socket can be half-open: status stays `connected`, nothing arrives,
and `useWatchdogReload` never trips because status never becomes
`disconnected`. Pusher-js covered this with its activity timeout; the
replacement does not. The watchdog also resets its "down since" stamp every
time the socket passes through `connecting` (`useWatchdogReload.js:36-42`), so
a screen that cannot connect at all never reloads either.

Fix: record `lastRxAt` on any message; in the ping interval, if more than two
ping periods have passed with nothing received, `sock.close()` so the backoff
path runs. Add a 10 s connect timeout. Make the watchdog track "not connected
since" and clear it only on `connected`.

### 4. Service worker will cache `/api` on the one site (lobby)

`lobby/src/sw.js:82-98`, `site/build.mjs:45`.

`build.mjs` writes `sync.json` as `{url: "<origin>/api"}`, so after switch day
the Worker is same-origin with `/lobby/`. The service worker passes through
only cross-origin requests, `?awanaBuild` probes and `version.json`; only
navigations and `.json` paths are network-first. `GET /api/v1/state` and
`/api/v1/calendar` fall to `cacheFirst`, so after the first success every
10-minute poll and every doorbell refetch returns the first cached body until
the next deploy. A `cache: 'no-store'` on the page fetch does not bypass the
service worker. The bearer-authenticated state body also sits in Cache
Storage.

Fix: return early for `url.pathname.startsWith('/api/')`. Better, make
cache-first an allowlist (`/assets/`, `shared/art`, `shared/brand`) and send
everything else to the network. Add an `sw.test.js` case for `/api/v1/state`.

### 5. Duplicate guard records after the print (print server)

`server.js:3786` (check) and `:3944` (record, after `await printLabel`). The
leader path has the same shape at `:5839`.

A second request arriving while the first is at any await between those lines
(`resolveImageBuffer`, `loadImage`, the receipt TCP path) passes
`isDuplicatePrint` because nothing has been recorded yet. Two labels, two
history rows, two sealed `checkin` celebrations. The window is widest in
receipt-printer mode, and the extension's retry at 38 s lands in it whenever
a print is slow.

Fix: an `inFlight` set claimed at check time and released in `finally`.

### 6. Nothing is "per night" (lobby)

`lobby/src/hooks/useTally.js:35`, `lobby/src/App.jsx:307-314, 385-394, 454,
1477`, `lobby/src/lib/cornerInfo.js:83`, `lobby/src/lib/firstOfNight.js:66`.

`useTally` loads the count once with `useState(load)` and never re-checks the
day, so from Thursday to Tuesday the corner reads last Wednesday's number. The
`fired*` and `prev*` refs (night, club, book and award milestones, "doors are
open") are cleared only by a page load or the Settings tally reset, so the
25/50/100 milestones fire on the first club night after a load and never
again. `isFirstOfNight` requires `count === 0`, which is false until the first
tally of the new night arrives.

Fix: App already owns `todayStr`. On a change of `todayStr`, reset the tally
and clear every per-night ref, ideally in one `useNightLedger(todayStr)` hook.
Add a vitest that advances the day with fake timers.

### 7. Tray says "running" before the bind (printer app)

`printer/electron-app/main.js:621-622`, `printer/print-server/server.js:8627-8651`.

`startListening()` returns the first `app.listen` object synchronously and the
tray flips to Running. The real bind is asynchronous, retries `EADDRINUSE`
five times over about 20 s, and finally only `console.error`s, which a
packaged Windows app never shows. If a retry succeeds, the app still holds the
first, dead server object, so Restart and Save close the wrong one and the
live listener keeps its old bind host. There is no periodic health probe and
no log file.

Fix: make `startListening` return a promise for the live server and set
`serverState` from it; track the live server inside `server.js` and close the
previous one first; probe `/health` every 30 to 60 s and restart with a tray
warning after two failures; write a rotating log.

### 8. The switch-day runbook contradicts the repo

`SWITCH.md:26-33`, `printer/VERSION` (7.10.0), `site/updates/printer/latest.yml`
(7.10.0), `lobby/desktop/package.json` and `site/updates/lobby/lobby.yml`
(1.1.0), tag `desktop-v1.1.0` already exists.

The runbook says to release printer 6.22.0 and sound room 1.1.0 as the bridge.
The printer feed already serves 7.10.0 and `printer-release.yml` demands
`VERSION == input`, so you would have to bump the app down. electron-updater
never downgrades, so a feed that drops to 6.22.0 stops every updated laptop
from updating, silently. The desktop tag already exists, so step 2 fails with
"already exists". What the church laptops actually run (the old repo's last
release) needs to be confirmed before the bridge versions are chosen.

Fix: rewrite the two bridge steps with versions above what is installed, and
add a guard to both release workflows that refuses to write a feed whose
version is not greater than the current one.

### 9. Self-update wedges on a superseded build (lobby)

`lobby/src/hooks/useBuildReload.js:65-77`.

Once `pending` is set to build X, `step()` never re-reads `version.json`. If
build Y deploys while the screen is busy (every push to main deploys), the HTML
probe returns Y, `deployed !== pending` is true, and the function returns.
It repeats every 15 s with `pending` stuck on X, so the screen never reloads.
Two pushes during one evening is routine.

Fix: when `deployed` differs from `own`, accept it as the new `pending` and
reload. Only `deployed === own` means "stale CDN, wait".

### 10. No supervisor on the Pi (Journey)

`journey/PI_SETUP.md:73` (`Exec=chromium-browser --kiosk ...`).

The page has careful in-page recovery, but if Chromium is OOM-killed, the tab
crashes or hangs, no JavaScript runs to recover it. The autostart launches the
browser once, with no restart loop, no hardware watchdog, no nightly reboot
and no `--noerrdialogs --disable-session-crashed-bubble` flags. A dead screen
stays dead until someone brings a keyboard. The same file still tells
volunteers to edit the old `Journey-Display` repo.

Fix: a wrapper script or user systemd unit with `Restart=always`, the Pi
hardware watchdog, a nightly reboot at a quiet hour, the kiosk flags, and the
corrected path.

## Everything else, by area

### Print server (`printer/print-server/`)

- **Medium-High. `config.json` is written in place** at `server.js:6781, 7958,
  7987, 8173` while every other store uses tmp+rename. A truncated file makes
  the Electron wizard treat it as first run and merge over `{}`, losing the
  PIN, display key, sync session and schedule. Add one `atomicWriteJson`
  helper with fsync and a `.bak`, refuse to write on a parse failure, and
  guard the unguarded `JSON.parse` in `writeConfigPatch`.
- **Medium-High. Printing a worksheet PDF changes the Windows default printer
  permanently** (`SetDefaultPrinter`, `server.js:6039`). On installs where the
  label printer is "system default", every label after a mid-club worksheet
  goes to the letter printer. Use `PrintTo` with the printer name, or restore
  the old default in a `finally`.
- **Medium. The live-channel relay queue is unbounded and strictly serial with
  a 15 s timeout per frame** (`server.js:6789-6801`, `sync-client.js:27`).
  With the internet down, a 60-child rush builds a backlog that takes about 30
  minutes to drain, and callers that await `events.publish` hang with it.
  Bound the queue, keep only the newest tally/recap/birthdays frame, drop
  check-ins older than about 2 minutes, add a circuit breaker, and run only
  one sign-in check at a time.
- **Medium. `MAX_HISTORY = 200` is counted over every row type** (failures,
  reprints, leader tags, jam reprints), so a busy night can evict tonight's own
  check-ins, undercounting the tally and leaving children out of the CSV
  re-import. Never evict rows from today.
- **Medium. A failed rename on Windows silently loses a row**
  (`saveHistory` 4112-4122 and three siblings). Retry on `EPERM`/`EBUSY` with
  backoff and raise a `/health` warning if it still fails.
- **Medium. Phone relay is one request at a time; jam and range reprints have
  no re-entry latch** (`phone-relay.js:56-80`, `server.js:5505-5530`). A jam
  reprint can hold every phone for 60 s, and a second tap starts a second
  interleaved loop. Add a busy latch that answers 409; run two or three relay
  requests in parallel.
- **Medium-Low. The print path can throw outside its `try`**
  (`server.js:3794-3853`, before the `try` at 3865; Express 4 does not catch
  async rejections). The client gets no reply until its timeout and the retry
  hits the same throw. Wrap the enrichment, and add an async `wrap()` to every
  route.
- **Medium. Pusher client has no request timeout** (`server.js:138-145`).
  Matters until switch day: add `timeout: 10000`.
- **Low.** The recap buffer never rolls over at midnight in a week-long
  process; `downloadImage` has no error handler, size cap, or `resume()` on
  non-200; `isNewKid` is off by one across spring-forward; some lookups match
  by name only, so same-named children share flags; relay failures do not
  show on `/health` while Pusher is configured; `displayOrigins` defaults to
  only the github.io origin and the legacy version check allows downgrades.
- **Performance, High. Every history row stores the club logo as a base64
  PNG** (`server.js:4426`), and the whole file is re-read synchronously
  several times per check-in, every 15 s by the dashboard, every 12 s per
  phone, and rewritten pretty-printed on each check-in. Store one icon per
  club by hash and reference it; drop the blobs from `/history*` responses.
- **Performance, Medium.** History and the attendance ledger are re-read from
  disk at about 25 call sites instead of held in memory; the ledger walk never
  prunes. `loadClubbers()` re-parses the CSV and logs child names on every
  call (check `mtime` first). `generateLabel` writes a temp PNG even for
  previews, and the client logo goes through `prepareLogoForThermal` on every
  print.
- **Structure.** `server.js` is 8,760 lines with clear seams: config store
  (shared with Electron), label rendering (already pure), print backends (where
  the async rewrite lives), stores with in-memory caching, tonight logic,
  publisher with the relay queue, and Express routers. `module.exports` has
  become the test API.

### Chrome extension (`printer/chrome-extension/`)

- **High. Every extra TwoTimTwo tab prints its own duplicates.** Dedup state is
  per-tab `sessionStorage` (`content.js:219-221`); the manifest matches every
  path on the host; a second tab seeds its baseline 60 s after load and then
  reconciles every check-in made elsewhere as "missed". Run the print
  machinery only on the check-in page, elect one leader tab with
  `navigator.locks`, and share `printedNames` through `localStorage` keyed by
  date.
- **Medium. One exception in the 2,200-line `injectWidget` kills detection,
  polling and the queue flush** (`content.js:806`, call site `:4877`,
  unguarded). Wrap each boot step and start the critical steps before the
  widget.
- **Medium. The peak-window `autoRefresh` guard is a presence check**
  (`content.js:3961`, `getElementById('checkin-modal')`), and that element
  appears to be static markup, so the 5:40 to 6:00 reload probably never
  happens. If it did, it would cancel the first-reconcile timer. Test
  visibility, and add in-flight guards.
- **Medium. Children whose name contains "undo" never get a label**
  (`isUndo` at `content.js:315` is a bare substring; Mundo, Dundon, Fundora).
  Detect undo structurally on the link, not on name fields.
- **Medium. Phone actions have no claim step**, so two tabs both execute them,
  and the poll spins every 500 ms while one is pending (`content.js:4243`).
  Add a server-side claim with a lease.
- **Medium. A direct check-in the server accepted but "didn't confirm" is
  POSTed again** (`content.js:623-625`, success requires the first name in
  the response text). Treat 200 as posted and verify before retrying.
- **Medium. Three loops poll the same TwoTimTwo pages**, and `ymSweep` retries
  a failing child every 30 s all night. Share one cached fetch of the report;
  cap retries per child.
- **Medium. Award slips and worksheets are marked done before the print is
  known to have worked** (`feeds.js:429-435, 696-707`). Mark on `r.ok` only.
- **Low.** Untimed fetches in `fetchShareBalances`, `syncCsv`, `popup.js`;
  `onCheckin` skips the name fallback that `isPrinted` has; the `#lastCheckin`
  observer can watch a detached node; Store-night detection is a generic
  `/store/i` substring; `awanaYmOut.*` keys and `phoneActionsInFlight` are
  never pruned; all localhost traffic goes from the content script and is
  exposed to Chrome's Local Network Access gating.
- **Performance.** Per-row base64 logos bloat `sessionStorage` (about 6
  distinct logos copied into every row); the 2 s roster scan does full DOM
  reads and a `JSON.stringify` plus storage write all night against a page
  that never changes.
- **Structure.** `content.js` (4,973 lines) splits cleanly into state, queue,
  widget, detection, print path, reconcile, phone executor and boot. The
  manifest already loads three classic scripts, so a shared `window.__awana`
  namespace is enough; no bundler needed. There is no jsdom harness today, so
  none of the queue, reconcile or refresh logic is tested.

### Lobby signage (`lobby/src/`)

- **High. No root error boundary** (`main.jsx:46-52`). Only the stage layers
  are fenced; `buildCalendarSlides`, `resolveSkin`, `lobbyRoom`, `decideBoard`
  and several chips compute in App's own render. A throw there blanks the
  screen with nothing left running to reload it. Add a root boundary with a
  branded fallback and a capped auto-reload.
- **Medium. No fetch timeouts, and the coalescing guards turn one hung request
  into a permanent stall**: `syncRequest` (`syncService.js:118-136`) with
  `syncNow`'s shared `inFlight`, `useCalendar.load` with `busy.current`, plus
  the remote config, schedule, theme, weather and PPTX fetches. One
  `fetchWithTimeout` helper everywhere.
- **Medium. The printer's `at` is still compared with the TV's clock outside
  the tally path** (`freshness.js:15`, `checkoutBoard.js:127`, `App.jsx:493`).
  A TV 10 minutes fast hides the tonight strip; 20 minutes fast makes recap
  discard every missed child. Stamp `receivedAt` where each payload lands.
- **Medium. Service worker cache lifecycle**: old caches are deleted on
  activate while a busy page may still lazy-load an old club SVG or font that
  the precache regex (`js|css|woff2?`) excluded; the build hash ignores
  `public/` and `shared/`, so a deploy that only changes art keeps serving old
  bytes; `networkFirst` has no timeout, so a lie-fi navigation hangs instead
  of falling back to the shell.
- **Low.** `setSharedLocally` throws on an empty `publishedAt` and leaves the
  share status stuck on "sending"; the video slide restarts on every parent
  render (inline ref callback); the slide hold timer uses `Date.now()` deltas;
  self-update is blocked indefinitely by an open panel or a STALE board;
  weather is kept forever after an outage; audio chimes queue while the
  context is suspended; `ensureUrl` caches `''` for the page's life if
  `sync.json` is unreachable at boot; the wake lock is never re-acquired after
  an OS release.
- **Performance, Medium.** One 285 KB gzip bundle with no code splitting:
  `jszip`, Settings, the slide editor, Debug and four promo posters all load
  on every TV and Pi boot. `React.lazy` the panels and dynamic-import
  `pptxHandler`. App has about 35 state hooks and no `React.memo` in the
  signage tree; four independent 30 s clocks each re-render the whole stage.
  Fold them into one clock and memo the stage leaves.
- **Low.** `CountdownTimer.jsx` and three fontsource packages (caveat,
  nunito-sans, barlow-condensed) are unreferenced. Season promos and flagship
  hours are hard-coded to 2026 (documented).

### Sync Worker, site, CI

- **Medium. `cancel-in-progress: true` at workflow level kills the deploy job
  mid-publish** (`ci.yml:19-21` vs the job-level deploy group). The release
  and bot workflows dispatch CI right after a push, so a cancel between
  `wrangler deploy` and `pages deploy` leaves the Worker new and the site old.
  The run history shows nearly every code push's run cancelled by the
  following feed commit. Use
  `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`.
- **Medium. Every push redeploys the Worker and re-uploads its secrets**
  (`ci.yml:173-203`), which restarts the Durable Object twice and drops every
  screen's socket, on nightly bot runs and Wednesday pushes alike. Gate on a
  changed-path check for `lobby/worker` and `lobby/src/lib`.
- **Medium. `site/build.mjs` runs only inside the main-only deploy job, after
  the Worker has shipped.** Its hard failures never run on a PR. Add a `site`
  job and order deploy as build, Worker, Pages.
- **Medium. Both release workflows push the tag before tests and build run**,
  so a failure leaves a tag behind and the retry dies on "already exists".
  Let the release action create the tag at the end.
- **Medium. Neither release workflow checks that the feed version goes up**
  (see #8).
- **Medium. The relay poll writes storage on every call** (`relay.js:110`):
  about 4,300 row writes a day idle from one always-on laptop, against the
  free-tier daily cap. Write `relay:laptop` only when it is more than 15 s
  old; skip `purge()` when the lists are empty.
- **Medium. Request bodies are fully buffered before any size check**
  (`index.js:133`, `sync.js:383-393`), including on the public login route,
  and the cap compares UTF-16 length not bytes. Reject on `Content-Length`
  early.
- **Medium. The Pages Function on `/journey/*` runs for every static request**
  because there is no `_routes.json`. Have `build.mjs` write one that includes
  only `/api/*` and the large-file prefixes.
- **Medium. `proxyLarge` drops conditional headers and maps every upstream
  error to 404** (`proxyLarge.js:44-47`). A GitHub 429 or 502 looks like a
  missing video and may be cached as such. Forward `If-None-Match`/`If-Range`,
  pass 304 through, and map 429/5xx to 502/503.
- **Medium. The nightly lesson bot commits a 24 MB mp4 to history every time
  it changes** (`journey-update-lesson.yml:77-80`); about 1.2 GB a year.
  Upload it to the `journey-videos-v2` release instead and commit only the
  JSON.
- **Low-Medium.** `SITE_ORIGIN` silently falls back to `pages.dev`; the
  relay purges a taken-but-unanswered request at 45 s while the laptop's own
  timeout is 60 s (a slow jam reprint answers into a 404 and the phone has
  already been told to retry); "Refresh calendar now" is unthrottled and its
  failure path can overwrite a newer calendar; `webSocketError` is a no-op and
  there is no per-session socket cap; `fails:<ip>` keys are never pruned; the
  calendar bot's push has no rebase-and-retry; no `timeout-minutes` on any job
  but one; the root CI dropped the lobby's `e2e:events` and `e2e:visual`
  suites; deploy runs three uncached `npm ci` plus a second build on Node 22
  of apps tested on Node 20; the printer release's 30-minute "wait for live
  feed" and Pusher `update` ping are dead weight; the delete workflows do not
  check whether the feed still points at the tag; hashed assets get Pages'
  default `max-age=0`.
- **Docs drift.** `wrangler.toml` and `worker/README.md` still describe the
  dormant `deploy-worker.yml` and Pusher; `ALLOWED_ORIGINS` still lists
  github.io; `workers_dev = true` leaves a second public address.

### Printer app (`printer/electron-app/`)

- **Medium.** Modal dialogs sit on the unattended boot path ahead of the
  server (`main.js:836-861`); on an auto-start with the port busy, printing
  waits for a human click. Start the server first, show conflicts in the tray
  when `isAutoStart`, wrap the boot sequence.
- **Medium.** `installInFlight` is never reset (`main.js:172-214`), so one

- **Low.** A failed extension sync can leave a mixed-version folder the next

- **Dependencies.** Electron `^28` and electron-builder `^24` versus the sound
  room app's `^44` and `^26`. Electron 28 is out of Chromium security support
